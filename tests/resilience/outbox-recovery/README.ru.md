# Resilience: outbox recovery

*[English version](README.md)*

Второй resilience-тест (см.
[`docs/architecture/testing-strategy.ru.md`](../../../docs/architecture/testing-strategy.ru.md)).
Не бизнес-сценарий и не граница — конкретное утверждение о поведении
при сбое: реально ли `billing-outbox` догоняет строки, которые он
пропустил, пока был остановлен, а не теряет их или требует повторного
проведения исходной записи. Это вторая половина того, что обещает
паттерн Transactional Outbox — первая половина (доменная запись и её
строка Outbox коммитятся вместе, синхронно) неявно присутствует в
любом другом тесте, который его использует; этот — единственный, что
реально останавливает relay, чтобы проверить остальную часть обещания.

## Почему тест сам управляет Docker

Остановка и перезапуск `billing-outbox` посреди сценария — это и есть
тест, а не подготовка к нему, поэтому это происходит внутри `composer
test` через
[`tests/Support/DockerCompose.php`](tests/Support/DockerCompose.php)
(тонкая обёртка над `docker compose stop/start`), а не как ручной шаг,
который иначе пришлось бы описывать в README. Пока локально в этом
тесте, не в [`tests/support/`](../../support/) — та же дисциплина
extraction, что и у `eventually()`: копируем для первых двух
resilience-тестов, которым нужно управление start/stop
(`rabbitmq-outage/` почти наверняка понадобится), делимся на третьем.

## Что реально доказано, и почему важен порядок

`billing-outbox` останавливается *до* того, как что-либо создано —
строка Outbox, о которой этот тест, должна быть записана, пока relay
доказанно не запущен, а не гнаться за relay, который просто ещё до неё
не добрался. `billing-consumer` вообще не нужен `billing-outbox`, чтобы
делать свою работу: `CreateInvoiceHandler` коммитит Invoice и его
строку Outbox в одной транзакции, совершенно независимо от того,
релеит ли сейчас что-то старые строки — это реальное, полезное
свойство паттерна, продемонстрированное мимоходом тем, что первая
проверка этого теста вообще проходит. Как только `billing-outbox`
запускается обратно (тот же самый контейнер, перезапущенный — не
свежая замена, и не повторная исходная транзакция), `eventually()`
подтверждает, что пропущенная строка доходит до wire.

## Что поднимается

| Сервис | Роль |
| --- | --- |
| `postgres` | один инстанс |
| `rabbitmq` | настоящий брокер — AMQP-порт опубликован наружу, поскольку тест публикует seed-событие и напрямую читает восстановление |
| `billing-api` | отдаёт `GET /invoices` для проверки в тесте |
| `billing-consumer` | настоящий цикл `billing-events:consume` — доказывает, что работает с остановленным relay |
| `billing-outbox` | настоящий Outbox relay — то, что проверяется, останавливается и перезапускается самим тестом |

## Запуск

```bash
cd tests/resilience/outbox-recovery
composer install
docker compose up -d --build
composer test
docker compose down --volumes
```

## Проверено вживую: реальная остановка, не симулированная

`docker compose ps` сразу после прогона теста показал `billing-outbox`
как `Up 6 seconds` у контейнера, `Created` 35 секунд назад — реальный
цикл остановки и перезапуска, не no-op. Остановленный контейнер вообще
не может логировать, так что каждая строка `Published 0 outbox
message(s).` в его логах — либо до остановки, либо после перезапуска;
среди них есть ровно одна `Published 1 outbox message(s).` — строка,
которую он пропустил, найденная, как только он снова заработал.
