# Resilience: consumer crash

*[English version](README.md)*

Четвёртый и последний запланированный resilience-тест (см.
[`docs/architecture/testing-strategy.ru.md`](../../../docs/architecture/testing-strategy.ru.md)).
Не то же самое утверждение, что уже доказал
[`duplicate-delivery/`](../duplicate-delivery/) (что Inbox игнорирует
точный дубликат `event_id`, независимо от того, как этот дубликат
возник) — этот тест доказывает, что сам *механизм*, производящий такой
дубликат в production, реально работает end-to-end: процесс падает с
сообщением, за которое уже закоммитил, но так и не подтвердил (ack),
RabbitMQ замечает обрыв соединения и передоставляет сообщение, а
реальный, перезапущенный консьюмер реально натыкается на guard Inbox.

## Почему потребовалось небольшое осознанное изменение в `billing-service`

Каждый другой resilience-тест управляет Docker или wire снаружи
приложения — этот первый, кто не мог так, и стоит честно объяснить,
почему. Окно между коммитом транзакции в `CreateInvoiceHandler` и
вызовом `$message->ack()` в `ConsumeBillingEventsCommand` обычно —
микросекунды, слишком узко, чтобы любой внешний тест (следящий за
логами, выпускающий `docker kill`) мог надёжно туда попасть. Два
маленьких, аддитивных изменения в `ConsumeBillingEventsCommand` делают
это окно наблюдаемым и управляемым:

1. Строка лога — `"Processed event {event_id}, acking."` — сразу
   после того, как handler вернулся, и прямо перед ack. Сама по себе
   полезна для production-диагностики зависшего ack, не только как
   тестовый хук.
2. `CONSUMER_CRASH_TEST_DELAY_MS`, переменная окружения, читаемая один
   раз прямо перед ack: `if ($delayMs = (int) env(...)) { usleep($delayMs * 1000); }`.
   Не задана (`0`) в любом реальном окружении, включая любой другой
   `docker-compose.yaml` в этом репозитории — только стек этого теста
   задаёт её (в `5000`), расширяя окно с микросекунд до секунд, чтобы
   [`LogWatcher`](tests/Support/LogWatcher.php) мог надёжно увидеть
   строку лога, а
   [`DockerCompose::kill()`](../../support/src/DockerCompose.php) —
   попасть `SIGKILL`-ом до ack, а не после — именно это гонял бы и
   почти всегда проигрывал бы наивный подход «следить за логами, потом
   убить» без этого изменения.

Оба изменения аддитивны и выключены по умолчанию; любой другой тест и
любой реальный деплой не видят вообще никакого изменения поведения.

## Что поднимается

| Сервис | Роль |
| --- | --- |
| `postgres` | один инстанс |
| `rabbitmq` | настоящий брокер — AMQP-порт опубликован наружу, поскольку тест публикует seed-событие напрямую |
| `billing-api` | отдаёт `GET /invoices` для проверок в тесте |
| `billing-consumer` | то, что проверяется — убивается (`SIGKILL`, без graceful shutdown) и перезапускается самим тестом, с заданным `CONSUMER_CRASH_TEST_DELAY_MS` |

## Запуск

```bash
cd tests/resilience/consumer-crash
composer install
docker compose up -d --build
composer test
docker compose down --volumes
```

## Проверено вживую: ровно та сигнатура в логах, что даёт настоящий crash-and-recover

`"Processed event <id>, acking."` встречается в логах
`billing-consumer` **дважды** для одного события, которое публикует
этот тест — один раз для убитой попытки (которая так и не доходит до
следующей строки), один раз для передоставленной попытки, которая
реально завершается — при этом `"Consumed 1 message(s)."` (достижимо
только *после* успешного ack) встречается ровно **один раз**. `docker
compose ps` сразу после прогона показал контейнер `Up` меньше времени,
чем он вообще существовал — реальный kill-and-restart, не no-op.
Вместе это и есть сигнатура сообщения, которое с точки зрения RabbitMQ
реально было обработано дважды, а с точки зрения базы данных реально
закоммичено лишь один раз — доказано настоящим падением, а не второй
ручной публикацией.
