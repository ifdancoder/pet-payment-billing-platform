# Architecture Decision Records

*[English version](README.md)*

ADR — это краткое описание одного значимого решения: что к нему
привело, что именно было решено и какова цена решения. Записывайте ADR
один раз, когда решение принято, и не редактируйте его задним числом.
Если решение перестало быть актуальным, создайте новый ADR, который
заменяет старый, вместо изменения исходного документа.

## Когда нужен ADR

Пишите ADR для решений, которые трудно отменить, которые затрагивают
несколько сервисов или которые будущему участнику проекта (в том числе
вам самим) иначе пришлось бы восстанавливать по коду. Например: выбор
брокера сообщений, границы database-per-service, синхронное или
асинхронное взаимодействие в конкретном процессе, выбор ingress-
контроллера или оператора в `infrastructure/kubernetes/`.

Повседневные решения, которые легко изменить позже, в ADR не нуждаются.

## Формат

Один файл на решение, с именем `NNNN-short-title.md` (номер дополнен
нулями и последовательно увеличивается), примерно по классическому
шаблону Найгарда:

```markdown
# NNNN. Заголовок

## Статус

Предложено | Принято | Заменено на NNNN

## Контекст

Что вынуждает принять решение: технические, бизнесовые и командные
ограничения. Здесь должны быть факты, а не само решение.

## Решение

Что решено — простым языком и в активном залоге.

## Последствия

Что становится проще, а что сложнее. Компромиссы и дальнейшая работа,
а не только преимущества.
```

## Языки

У каждого ADR есть английская каноническая версия и русский перевод
рядом с ней: `NNNN-short-title.md` и `NNNN-short-title.ru.md`. В начале
каждого файла находится ссылка для переключения языка.
