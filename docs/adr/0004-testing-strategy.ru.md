# 4. Стратегия тестирования: пирамида и где какой уровень запускается

*[English version](0004-testing-strategy.md)*

## Статус

Принято

## Контекст

У каждого сервиса уже есть тесты, но все они лежат под тремя именами на
сервис — `Unit`, `Integration`, `Feature` — и ничто на уровне монорепо
не проверяет то, что на самом деле делает эту систему распределённой:
что Outbox Subscription реально доходит до Inbox Billing через
настоящий RabbitMQ, что повторная доставка реально становится no-op,
что весь бизнес-флоу `Subscription → Invoice → Payment → Notification`
реально завершается.

«Добавить ещё тестов» — это не решение само по себе. Три принципиально
разные вещи получали одинаковое обращение:

- «делает ли этот Handler правильные вызовы против fakes» (быстро, без
  инфраструктуры, должно запускаться на каждый коммит)
- «действительно ли этот Eloquent-репозиторий корректно проходит
  туда-обратно через Postgres» (нужна настоящая инфраструктура, но всё
  ещё один сервис)
- «завершает ли вся платформа покупку» (нужны все сервисы, дорого, не
  должно блокировать каждый коммит)

Смешение их даёт либо слишком медленный для локального запуска сьют,
либо сьют, который пропускает именно тот уровень, что доказывает
работоспособность distributed-systems паттернов (Outbox, Inbox,
eventual consistency).

## Решение

### Уровни

Тест относится ровно к одному из следующих уровней, в зависимости от
того, что ему реально нужно запущенным — а не от того, в какую
директорию его удобнее положить:

| Уровень | Что проверяет | Реальная БД | Реальный RabbitMQ | Другие сервисы |
| --- | --- | --- | --- | --- |
| Unit | доменную сущность или value object | нет | нет | нет |
| Application | Handler/use case, против fakes | нет | нет | нет |
| Integration | один адаптер (репозиторий, HTTP-gateway, RabbitMQ publisher) | да | иногда | нет |
| Component | целый сервис, его собственная HTTP/console-граница | да | да | stub |
| Contract | схему одного события, со стороны producer или consumer | нет | нет | нет |
| Service integration | 2-3 сервиса через реальный брокер | да | да | да (2-3) |
| E2E | полный бизнес-флоу по всей платформе | да | да | да (все) |
| Resilience | конкретный failure-сценарий (crash, redelivery, outage) | да | да | да |

Unit- и Application-тестов должно быть заметно больше, чем всех
остальных вместе — именно они реально ловят сломанное бизнес-правило,
и запускаются бесплатно. Каждый уровень ниже Integration становится
дороже и отвечает на всё более узкий вопрос; ни один из них не
заменяет уровень выше «просто запустив то же самое с реальной
инфраструктурой вместо fakes».

### Как это ложится на то, что уже есть, по сервисам

Никакого механического переименования по семи сервисам ради одного
этого решения — существующие сьюты уже аккуратно ложатся на уровни:

- `tests/Unit/Domain/` → **Unit**
- `tests/Integration/Application/` → **Application** (имя директории
  появилось раньше этого ADR — но уже сейчас в каждом сервисе означает
  «Handler + fakes, без инфраструктуры», то есть ровно то, что эта
  таблица называет Application)
- `tests/Integration/{Gateways,Messaging,Persistence,Transaction}/` →
  **Integration** (реальный Postgres через собственную тестовую БД
  сервиса, реальное соединение с RabbitMQ там, где адаптеру оно нужно)
- `tests/Feature/{Http,Console}/` → собственный идиоматичный Laravel
  in-process тест цикла запроса: настоящий
  routing/middleware/FormRequest/Controller, `Http::fake()` для
  исходящих вызовов. Отличается от **Component** ниже (отдельно
  запущенный живой процесс, к которому обращаются по сети, с живым
  stub-сервером вместо зависимостей) — оставляем оба, они отвечают на
  разные вопросы.
- `tests/Architecture/` → без изменений, проверяет правила направления
  зависимостей, которых требует Clean Architecture.

**Component**, **Contract**, **Service integration**, **E2E** и
**Resilience** — новые. Service integration и E2E/Resilience не
принадлежат `tests/` ни одного отдельного сервиса — они живут в корне
монорепо, потому что запуск тестов одного сервиса не должен требовать
сборки и поднятия шести остальных.

### Структура тестов в монорепо

```text
tests/
├── integration/            # Service integration: 2-3 реальных сервиса, реальный брокер
│   ├── subscription-to-billing/
│   ├── billing-to-payment/
│   └── payment-to-billing/
├── e2e/                     # Полные бизнес-флоу, все сервисы, fake providers
│   ├── successful-subscription/
│   ├── failed-payment/
│   └── overdue-subscription/
└── resilience/              # Конкретный failure-сценарий, а не бизнес-сценарий
    ├── duplicate-delivery/
    ├── consumer-crash/
    ├── rabbitmq-outage/
    └── outbox-recovery/
```

Каждая директория `tests/integration/<slice>/` и `tests/e2e/<scenario>/`
— это свой маленький самостоятельный проект: `docker-compose.yaml`,
поднимающий ровно те сервисы, что нужны этому сценарию (не все семь,
если это не полный E2E), и Pest-проект со своим `composer.json` — без
Laravel-бутстрапа, без общего vendor с каким-либо сервисом, поскольку
эти тесты — чёрные ящики, HTTP-клиенты уже запущенных процессов. Первый
такой тест —
[`tests/integration/subscription-to-billing/`](../../tests/integration/subscription-to-billing/).

### Асинхронные проверки: polling, а не sleep

Запрос, запускающий асинхронную цепочку (HTTP-вызов → Outbox →
RabbitMQ → отдельный процесс-консьюмер), нельзя проверить сразу — ответ
201 доказывает только первый шаг, а не то, что прошла вся цепочка.
Фиксированный `sleep(N)` перед проверкой одновременно медленный (всегда
платит худший случай) и всё равно нестабильный (нагруженный CI может
гонку проиграть). Каждый service integration, E2E и resilience тест
вместо этого опрашивает финальную проверку, пока она не пройдёт или не
истечёт таймаут — см. [`eventually()`](../../tests/support/src/eventually.php)
в общем пакете test-support.

### Проверка через HTTP, а не через залезание в чужую БД

Component-тест, проверяющий свою же БД своего сервиса — это нормально,
это проверка внутренностей самого сервиса. Service integration или E2E
тест, залезающий в схему другого сервиса (`SELECT * FROM
billing.invoices`) — нет: это привязывает тест к деталям внутреннего
хранения, от которых не имеет права зависеть ни один клиент, и сводит
на нет смысл database-per-service. Такие тесты вместо этого вызывают
собственный HTTP API другого сервиса (`GET /v1/invoices/{id}`) — точно
так же, как это сделал бы настоящий клиент.

### Fake providers, а не настоящие, для всего внешнего

E2E- и resilience-тесты не должны вызывать настоящий платёжный
процессинг или реально отправлять email. И Payment, и Notification
сервисы получают fake-адаптер провайдера, выбираемый конфигом
(`PAYMENT_GATEWAY=fake`, `NOTIFICATION_DRIVER=fake`), который
поддерживает детерминированные исходы (известный token/card →
success, decline или timeout), чтобы сценарии failure-путей были
реально воспроизводимы, а не зависели от настроения sandbox-провайдера.

### Docker Compose для бизнес-тестов, Kubernetes — для платформенных

Service integration и E2E тесты запускаются на Docker Compose, не на
Kubernetes — они доказывают, что работает бизнес-система, а не что
работает Kubernetes. Отдельно существует `kind`-based test suite,
который проверяет совсем другой набор вопросов: правильно ли роутит
Ingress, остаётся ли доступным rolling update, срабатывает ли CronJob,
реально ли масштабируется worker — инфраструктурные вопросы, не
бизнесовые. Там запускается один-два smoke-сценария бизнес-логики
(создать subscription, дождаться active), а не весь каталог E2E.

### Разделение в CI

Unit, Application, Architecture, Integration, Component и Contract
запускаются на каждый PR — весь этот набор должен укладываться в
единицы минут. Service integration тоже запускается на каждый PR,
только по тем срезам, которых касаются изменённые сервисы. Полный E2E
и Resilience слишком дороги, чтобы блокировать каждый коммит (поднять
семь сервисов плюс инфраструктуру), и запускаются на `main` и по ночам.

## Последствия

Становится проще: сломанное бизнес-правило падает в Application-тесте
за секунды после того, как написано, а не только в дорогом E2E-прогоне
через несколько минут. Добавление нового event-консьюмера означает
написать для него Contract test, а не надеяться, что следующий
E2E-прогон случайно его заденет. У distributed-systems паттернов, на
которых построена вся платформа — Outbox, Inbox, eventual consistency,
идемпотентная redelivery — теперь есть тесты, которые реально могут
упасть, если паттерн перестанет работать, а не только доказываются
вручную через curl к живому кластеру (именно так до сих пор
проверялась каждая межсервисная цепочка в этом репозитории).

Становится сложнее: больше движущихся частей, за которыми нужно
следить (к какому из восьми уровней относится новый тест), а Service
integration / E2E тестам нужны собственные Docker Compose стеки и
самостоятельные Pest-проекты, а не просто ещё один test-класс,
добавленный в существующий сервис. `docker compose build` для
четырёх-плюс сервисов добавляет реальное время локально и в CI, хотя
это всё равно намного дешевле альтернативы (узнать, что связка
сломана, только из ручного `curl` к живому кластеру или от клиента).

Дальнейшая работа, явно не сделанная этим ADR: оставшиеся service
integration срезы (Billing → Payment, Payment → Billing → Subscription
→ Notification), Component-тесты для любого сервиса, Contract-тесты
для каталога событий, полный каталог E2E, resilience suite, и
`kind`-based platform smoke tests. Строится по одному вертикальному
срезу за раз, так же, как и вся остальная платформа — живая версия
этого плана, по мере наполнения, в
[`docs/architecture/testing-strategy.ru.md`](../architecture/testing-strategy.ru.md).
