# Обзор архитектуры

*[English version](overview.md)*

Как устроена и взаимодействует платформа биллинга.

## Системный контекст

Платформа состоит из независимо разворачиваемых Laravel-сервисов,
которые вместе обслуживают биллинг, подписки и платежи мерчантов. Это не
монолит: каждая бизнес-возможность владеет своими данными и находится
за собственной границей сервиса.

Трафик поступает через единый API gateway (локально Nginx, в Kubernetes
— `Ingress` ingress-nginx, см. [`kubernetes.ru.md`](kubernetes.ru.md)) и
направляется в нужный сервис. Таблица маршрутов, разделение публичных
`/v1/...` и внутренних `/api/v1/...` путей и причина, по которой gateway
сам не аутентифицирует запросы, описаны в
[ADR 0001](../adr/0001-api-gateway-routing.ru.md).

## Границы сервисов

| Сервис | Ответственность |
| --- | --- |
| Identity Service | Аутентификация и авторизация мерчантов |
| Customer Service | Клиенты и платёжные профили |
| Catalog Service | Продукты, цены и скидки |
| Subscription Service | Жизненный цикл подписок |
| Billing Service | Инвойсы и биллинговые циклы |
| Payment Service | Платежи, возвраты и платёжные провайдеры |
| Notification Service | Асинхронные уведомления клиентов |

Все семь находятся в `services/`; каждый — независимо запускаемое
Laravel-приложение со своей базой данных. Подробнее о месте Docker и
Kubernetes в roadmap см. в [`kubernetes.ru.md`](kubernetes.ru.md) и
корневом README.

## Владение данными

Каждый сервис владеет своей моделью хранения и только он может в неё
писать. Ни один сервис не читает базу другого напрямую. Локально все
могут для удобства использовать один экземпляр PostgreSQL, но граница
владения логическая, а не физическая, и должна сохраняться при любом
способе развёртывания.

## Взаимодействие

- **Синхронное**: прямые HTTP-вызовы, когда вызывающей стороне нужен
  немедленный ответ.
- **Асинхронное**: интеграционные события через RabbitMQ для
  межсервисных процессов и распространения изменений состояния
  (например, изменение подписки запускает создание инвойса). Контракт
  сообщений — delivery semantics, envelope, naming и топология очередей
  — описан в [ADR 0002](../adr/0002-rabbitmq-messaging.ru.md), а все
  существующие события, их publishers и реальные consumers — в
  [`event-catalog.ru.md`](event-catalog.ru.md).

## Паттерны надёжности

Это не второстепенные детали:

- transactional outbox, чтобы события надёжно публиковались вместе с
  локальными изменениями;
- inbox / идемпотентные консьюмеры, чтобы повторная доставка не
  создавала дублирующие побочные эффекты;
- idempotency keys на изменяющих состояние клиентских endpoints;
- retries с dead-letter queues для сообщений, которые невозможно
  обработать;
- saga / process manager для процессов, охватывающих несколько сервисов
  и не помещающихся в одну локальную транзакцию.

## Слоистая архитектура каждого сервиса

Каждый сервис следует Clean Architecture / Hexagonal Architecture:

- бизнес-правила не зависят от Laravel, Eloquent, RabbitMQ, PostgreSQL
  или SDK платёжных провайдеров;
- зависимости направлены внутрь, к domain- и application-слоям;
- внешние системы (хранилище, брокер сообщений, платёжные провайдеры и
  другие API) подключаются через явные порты и адаптеры.

DDD применяется там, где это оправдано бизнес-моделью, а не как
обязательная структура повсюду.

## Наблюдаемость

Каждый сервис должен отправлять traces, metrics и logs через
OpenTelemetry. Сторона сбора и хранения — OpenTelemetry Collector,
Prometheus, Tempo, Loki и Grafana — подготовлена в
`infrastructure/kubernetes/platform/observability/`; см.
[`kubernetes.ru.md`](kubernetes.ru.md).
